# 删字段会不会伤缓存命中率

短答：**命中率只看 token 前缀，不看请求体字节数。** 所以"少传 1.9 MB"本身与命中率无关，
真正决定结果的是另一件事：删掉的这段文本，原本进不进 token 流，以及删的边界稳不稳定。

---

## 原理

prompt cache 的匹配单位是 token 前缀（按固定大小切块，64 token 量级）。
请求体里少一段不参与分词的字符，服务端算出的 token 序列完全一致 → 缓存照命中。

于是判断只需回答一个问题：**删掉这段，token 序列变了吗？**

## 按范式分开看

| 范式 | token 序列变化 | 对命中率的影响 |
|---|---|---|
| [可丢弃](paradigms.md#可丢弃) | **不变**（该字段从不进上下文） | **零** |
| [必须重放](paradigms.md#必须重放) | 变 | 取决于删除边界是否固定，见下 |
| [不透明凭证](paradigms.md#不透明凭证) | 变（且可能删错即报错） | 不建议删 |

"可丢弃"这一栏有一个很有力的实测证据：同一前缀加 14 万字符 cot，
`prompt_tokens` 与 `cache_hit` 都不变。也就是说这段文本原本就没进缓存中的 token 流。
**既然加进去不影响，拿掉它同样不影响。**

## 真正计入 token 的 provider：边界决定一切

| 删除策略 | 每轮缓存后果 |
|---|---|
| 边界逐步前移（`keepLast: 1` 的自然结果） | 上一轮保留的那条这一轮被删 → 从它之后失配。**稳定损失约一轮的量**，不是整段重算 |
| 一次性固定边界，只在缓存本来就会重置的时刻推进 | 已删集合不变 → 前缀稳定 → **命中率不受影响** |
| 每轮重新计算删哪些，结果不稳定 | 前缀反复抖动 → 最差情况**全段不命中** |

`keepLast: N` 之所以"只伤一轮"，是因为删除点永远在最后一条 assistant 附近：
它之后的内容本就要重算，损失被结构性地框在一轮之内。

反例是"清理历史中部大块内容"（例如外置图片）：改动点靠前，从那里往后全部失效。
那类操作必须有调度（只在缓存本就失效的时刻推进），否则收益被缓存损失吃掉。
**同一操作在 payload 层和语义层对缓存的影响相同，区别只在边界控制策略。**

## 三种真会拉低命中率的写法

1. **不幂等**。每个请求都过 handler，同一份 transcript 必须产出同一个 payload。
2. **改到缓存相关字段**。`prompt_cache_key`、Anthropic 的 `cache_control` 断点、
   system 数组结构 —— 这是直接和缓存机制对打，跟"删 cot 省流量"不是一类事。
3. **改动落在最后一条消息上**。那等于每轮把刚写下的东西再改一遍。

## 怎么自己验证

取 provider 返回的缓存计数字段，开/关 trim 各跑 5 轮以上：

- DeepSeek 系：`prompt_cache_hit_tokens`
- Anthropic：`usage.cache_read_input_tokens`
- OpenAI 系：`usage.cached_tokens`

看两件事：

- **命中绝对量**是否只掉一轮的量（→ 边界已固定，符合预期）
- **命中率**是否随轮次持续下降（→ 边界在移动，需要改成固定 watermark）
